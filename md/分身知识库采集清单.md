### 项目 A：云上米轨（百年滇越铁路数字化平台 · BtoBtoC）

**A.1 这个项目是什么？解决什么问题？**
本项目以“铁路数字文化遗产活化”为核心目标，立足新文科+数字技术交叉创新，由高校多学科青年团队自主研发，旨在以轻量化数字平台为载体，对云南米轨工业线性文化遗产开展系统性数字化保护与创新性活化。项目坚持问题导向、家国情怀、专业赋能，通过深入田野调研、史料整理、用户访谈，精准回应工业遗产保护难、传播弱、青年参与度低的现实痛点；融合城乡规划、数字媒体、计算机技术与文化产业等多学科知识，实现“专业知识——社会需求——数字技术”的深度转化，充分体现大学生创新创业教育的实践成效与综合能力提升。
项目遵循“资源整合—平台搭建——价值延伸”的闭环推进路径，创新构建“史料数字化—平台轻量化—传播大众化”的工业遗存活化新模式。首期建成云上米轨网页体验端，以轻量化开发实现米轨文化遗产云端沉浸式呈现，打破时空限制，让用户直观感受百年米轨历史风貌；同步构建标准化、可检索的米轨数字史料库，系统整合沿线历史文献、珍贵影像、工程档案与民间口述史，实现史料数字化存储与智能化管理，筑牢遗产保护数字根基；最终形成“线上体验+学术研究+研学传播+青年共创”的文化传播体系，缝合历史记忆与当代生活、学术研究与大众传播、文化保护与青年实践之间的裂隙，推动米轨文化从静态保护向动态传播、从馆藏封闭向大众共享转变，助力工业遗存活化与乡土文化传承。
在产业价值与社会价值层面，项目精准对接文旅融合与文化数字化战略，依托云南文旅市场复苏与知识付费意识崛起的双重机遇，聚焦文史研究人群与文旅研学群体两大核心客群，兼顾全国历史文化爱好者与文博机构，形成“专业研究+大众传播+青年传承”的多层次价值网络。项目既填补了西南米轨垂直领域数字化平台的空白，区别于传统文博网站静态展示与综合平台内容泛化的短板，又以青年视角重构文化叙事，增强青年群体对边疆历史、工业文明与民族文化的认同感与参与感，兼具文化遗产保护的社会价值、文旅产业升级的经济价值与大学生创新创业的育人价值，为同类工业遗产数字化活化提供可复制、可推广的青年方案。
在团队协作与落地性方面，项目与昆明理工大学建筑学院段文教授团队合作，由跨学科师生组成，专业互补、分工明确，具备扎实的学术基础与较强的实践执行能力；通过校企合作、文博机构共建、青年社群共创等方式整合资源，形成稳定的外部支撑体系，保障项目可持续运营与迭代升级，充分体现科教融汇、产教融合与专创融合的育人成效。
整体而言，云上米轨项目紧扣国家文化数字化战略与文旅融合发展方向，以创新破解难题、以专业赋能保护、以青年传承文化、以数字链接未来，兼具思想性、创新性、落地性与示范性，是新时代大学生厚植家国情怀、服务文化强国建设的生动实践。

项目解决的问题：
本项目聚焦云南米轨工业文化遗产传承与发展中的核心痛点，针对性解决当前核心问题，为百年米轨活化传承提供系统性解决方案，具体如下；
一是解决遗产保护乏力、史料流失的问题。当前滇越米轨实体遗产老化严重，老站房、桥梁、隧道等遗存缺乏专业修缮与常态化守护，面临自然损耗与人为荒废的双重风险；同时，大量历史照片、工程图纸、文献档案等史料散落于各地馆藏与民间，缺乏系统归集、数字化整理与永久存档，部分珍贵史料颜临失传。本项目通过数字化手段，实现实体遗产的虚拟复刻与史料的系统化归档，破解传统保护成本高、留存难、查阅不便的困境，实现遗产的长效保护与永续留存。
二是解决文化传播断层、受众覆盖面窄的问题。目前米轨文化传播形式陈旧单一，依赖线下展馆、纸质文献等静态方式，难以适配Z世代青年的沉浸式、互动式需求，导致年轻群体认知度低、参与感弱，文化传承出现断层。项目通过数字化、场景化传播载体，打破时空限制，让米轨文化走出山野与卷宗，触达更广泛受众，尤其吸引青年群体关注，打通文化传承的时代壁垒。
三是解决文旅体验浅层、价值挖掘不足的问题。当前米轨文旅开发停留在“打卡拍照”的浅层阶段，缺乏专业讲解、古今对比与深度文化解读，游客难以感知遗产背后的历史底蕴与人文价值，文旅体验同质化、单薄化。项目通过沉浸式场景构建，丰富文旅体验维度，实现从“观光式”到“深度体验式”的升级，挖掘米轨文旅价值。
四是解决研学服务缺失、学术价值难以释放的问题。米轨作为优质工业遗产研学资源，目前缺乏标准化研学路线、专业学术导引与公共交流平台，学校、文旅机构难以开展深度研学，文史研究者缺少成果分享与交流渠道，学术价值与教育价值未能充分激活。项目构建完善的研学服务体系，整合资源、搭建平台，释放米轨研学与学术价值。
五是解决商业变现不足、传承不可持续的问题。米轨文化IP未系统开发，文创产品零散无序，缺乏统一运营平台与成熟商业模式，无法通过商业收益反哺遗产保护与文化传播，导致传承工作缺乏长效资金支撑。项目搭建规范化商业运营体系，实现文化价值与商业价值的协同，为米轨活化传承提供可持续的资金保障。

**A.4【重点】你做了哪些关键产品决策？为什么这么决策？（尤其：怎么平衡 B 端和 C 端的不同诉求）**
>>> 他的关键决策按"平台战略、AI 设计、产品价值观"三层讲，每条都有真实的取舍过程。

【平台战略层 · B 端和 C 端怎么平衡】
这个项目本质是 BtoBtoC：B 端（博物馆 / 文旅局 / 学校）买的是史料数字化能力和研学服务，C 端（文史爱好者 / 研学群体）要的是好看好玩的体验。两端诉求有真实冲突——B 端要专业严谨、可管理、可定制；C 端要轻量、沉浸、低门槛。开发资源只有他一个人，怎么排序？他的解法是三条：

1. C 端体验先行，B 端底座同步。冷启动期 B 端客户不会为"一个想法"买单，他们要看到成型的平台和 C 端影响力。所以开发资源优先投向 C 端可感知的体验（交互地图、展览、AI 问答），但 B 端服务的底座从第一天就按"机构级"标准建——史料表的 era / category / status 元数据结构，就是未来给博物馆做"史料数字化服务"的标准化样板；Admin 后台按 5 部门角色分权（产品 / 技术 / 运营 / 商务 / 超管），是纯 B 端组织协作需求，但 Phase 2 就建好，因为向 B 端演示时必须让对方看到"机构怎么管理内容"。
2. 用一个机制同时满足两端：AI 引用回链。C 端用户要的是"答案可信"，B 端机构和学术用户要的是"可溯源"。他设计的引用回链（每条 AI 回答带 [1][2] 角标 → 渲染为档案卡片 → 点击直跳原始史料）用一个机制同时回应两种诉求，没有做两套系统。
3. 变现路径"展示但不深做"。VIP 会员、文创商城在当前阶段只做完整的入口和体系设计（6 级角色、商品架构），不做支付闭环——对 B 端和评审，这证明商业模式想清楚了；对开发资源，省下的时间全部投给核心体验。砍掉的不是能力，是优先级。

【AI 设计层】
4. RAG 而不是微调。四个理由：可解释性（引用回链的前提）、可维护性（新增史料 = 1 次 embedding，无需重训）、冷启动友好（早期史料仅百余条，远不够微调）、成本（微调一次 $1000+ vs RAG 边际成本趋零）。对一个考据型产品，"答案可溯源"是立身之本，这直接排除了纯生成方案。
5. 相似度阈值 0.40 的标定。初设 0.30 时，脱题问题也会硬召回 1-2 条弱相关史料，模型基于错位上下文生成似是而非的回答；提到 0.50 又会把表达不同但实质相关的史料过滤掉。0.40 是在测试集上反复跑出来的平衡点——低于阈值的召回强制丢弃，让模型"礼貌地说不知道"，宁可拒答不可编造。
6. 成本结构决策。DeepSeek V3（中文质量接近 GPT-4o、成本约 1/10）+ DashScope text-embedding-v3（中文语料表现最优 + 国内访问稳定），并通过 OpenAI 兼容协议接入——未来换模型是一行配置的事。实测单次对话成本约 $0.001。

【产品价值观层】
7. 数据真实性 > 视觉对齐（他最自豪的一条决策）。地图上 34 个站点坐标（来自学术论文）与 OSM 实测铁路线偏差 5-77 公里。他先实现了用 Catmull-Rom 样条把铁路线"硬掰"穿过站点——视觉完美了，但那是捏造的地理数据。他推翻了这版实现，保留真实偏差并留档说明。理由：平台的立身之本是考据严谨，为"看起来对"而造假，会摧毁 B 端机构和学术用户的长期信任。短期惊艳和长期信任之间，他选后者。

**A.5 用了哪些 AI 能力/技术？**
>>> 按"用了什么"和"怎么用好"两层说：

RAG 检索增强生成（核心）：
- Embedding：阿里 DashScope text-embedding-v3（1024 维），中文语料表现最优
- 向量检索：Supabase pgvector，cosine 相似度，top-4 召回 + 0.40 阈值过滤
- 生成：DeepSeek V3（deepseek-chat），通过 @ai-sdk/openai-compatible 以 OpenAI 兼容协议接入
- 流式输出：Vercel AI SDK v6 的 UIMessageStream——citations 作为 data parts 先于正文推送，前端在文本到达前就能显示"找到 N 条参考"

防幻觉与边界设计：
- 0.40 相似度硬阈值：低于阈值的召回强制不喂给模型，宁可"说不知道"也不基于弱相关上下文生成
- System Prompt 工程：领域限定 + 强制引用规则（答案必须带 [n] 角标）+ 拒答策略 + "据通识"标注机制（馆藏没有的内容明确标注来源不是档案，和档案内容区分开）
- 实测的意外收获：拒答时模型学会了"巧妙桥接"——被问巴黎奥运会，会顺势引到"滇越铁路的法国渊源与法式站房"，把越界问题创造性地拉回领域，这是 System Prompt 设计带来的产品级体验

产品化交互：
- 引用回链：AI 回答的 [1][2][3] 角标渲染为档案卡片，点击直跳原始史料详情
- Anchor 置顶：用户从某条史料的详情页进入 AI 对话时，该史料强制置为引用 [1]，模型优先围绕它解读——保证"从史料发起的提问"答得切题

评估体系：
- 自建 30 题 smoke test（域内 20 题 + 越界 10 题），三维度打分（事实正确 / 带引用 / 引用与问题相关），已脚本化、可随时回归

AI Coding：
- 全程 vibe coding，Claude Code 为主力——他的工作方式是"产品与技术决策自己拍板，代码实现由 AI 协作完成"

诚实声明：项目处于团队演示与汇报阶段，尚未对公众开放运营，没有真实用户流量、留存、转化数据。上述是工程质量与 AI 质量数据，不是业务数据。B 端客户签约、商业化验证均未开始——这些是下一阶段的事。

项目荣誉：入选 2026 年中国国际大学生创新大赛（研究生组）并获奖。

**A.7 你踩过的坑 / 最大的反思是什么？**
>>> 最大的反思（产品价值观层面）："不能为了表达牺牲数据的真实性。"
地图站点与实测线路偏差 5-77 公里时，他的第一反应是用算法把线"掰"到站点上——技术上做到了，视觉完美。但他随即意识到：这是在捏造地理数据，而这个平台的立身之本恰恰是考据严谨。他推翻了那版已经能跑的实现。这件事让他建立了一条产品红线：可信度是文化类产品的核心资产，宁可暴露数据瑕疵，不可制造虚假精确。这也是他在 Decision Notes 里最常对人讲的一条。

具体踩过的坑（每个都有教训）：
1. scp 部署后没验证，文件实际没传上去，线上还是旧版——他以为部署成功，排查了半天方向全错。教训：部署后必须在服务器上验证文件实际状态，不能信进度条；"我执行了"和"它生效了"是两件事。
2. 他自己忘了两次平台密码，才发现产品根本没做"找回密码"功能，被迫连夜补全整条流程（邮件重置 + 登录态修改密码）。教训：dogfooding 的价值——自己都会被锁在门外的产品，用户更会；账号体系的完整性不是"以后再说"的事。
3. 移动端适配滞后到演示前一天才暴露——观众要扫码体验，而多个页面在手机上大量错位。距离汇报不到 24 小时，全量适配必然来不及，他做了分级止损：核心演示路径（首页 / 史料 / AI）做真适配，次要页面加"建议横屏"提示条兜底。教训：演示场景的设备矩阵要提前定义，"在我电脑上是好的"是 PM 不能说的话。
4. 一个全局 CSS 入场动画（transform + filter）导致全站固定定位元素表现异常（移动端菜单"个人中心"按钮在部分页面消失），排查到 CSS containing block 的边缘行为才定位。教训：全局样式的隐性副作用比局部 bug 难查一个量级，改全局要有"爆炸半径"意识。
5. Google Fonts 被墙导致国内构建失败、ICP 备案周期（5-20 个工作日）挡住国内部署——最终方案是字体本地子集化 + 阿里云东京节点。教训：合规与网络约束要在架构阶段就纳入决策，而不是部署时才发现。

方法论沉淀（他会主动讲的三条）：
- AI 是调味料，不是主菜：南渡 AI 只占六分之一，承重的是史料、地图、社区。先想清楚用户旅程，再判断哪里值得加 AI——而不是反过来被"用 AI 做点啥"绑架。
- 决策要文档化：12 条 Decision Notes 让每个选择可追溯、可复盘。独立项目尤其需要，因为没有同事帮你记住"当时为什么这么定"。
- 约束驱动创新：备案约束 → 东京节点；字体被墙 → 子集化（4.5MB→87KB）；移动端时间不够 → 分级止损。每个约束最后都逼出了一个更好的方案。
