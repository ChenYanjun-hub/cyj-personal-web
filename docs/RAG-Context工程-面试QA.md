# 建景规 · RAG Context 工程 · 面试 Q&A

> 用途：AIPM 面试时被问到「长上下文 / token / context 工程 / RAG 优化」时的备答稿（第一人称，可直接复述）。
> 全部基于「建景规规范问答助手」真实做过的设计，不是背概念。
> 一句话定调：**我没把整个规范库塞进 prompt，而是把 RAG 全链路当成一套 context 工程——每一层都在管"喂给模型多少、喂什么"。**
> 维护：2026-06 · 对应 v2.0。

---

### Q1. 这个项目你是怎么处理"长上下文 / token 爆炸"的？

核心一句：**长上下文 token 爆炸的解法不是上更长的模型，而是 RAG 本身。**
我没把整个规范库（10785 条 chunk，估百万级 token）塞进 prompt，而是检索后只喂 Top5、每条 ≤800 字 ≈ 千级 token 上下文——把 context 从百万级压到千级，而且更 grounded。我把整条 RAG 链路当成一套 context 工程，分五层控制"喂多少、喂什么"。
（token 数为量级估算口径。）

### Q2. 具体是哪五层？

- **① 检索前 · 范围限定**：chunk 带 domain / spec_code 元数据，用户可按规范分类多选限定检索（Qdrant `MatchAny`），先把候选池从 89 部缩到指定几部。
- **② 检索 · 上下文选择**：BGE-M3 向量粗排 Top20 → BGE-Reranker-v2 精排 Top5 + 相关度阈值过滤。
- **③ chunk · token 预算单元**：以"条"为分块单元、单块 ≤800 字、表格/公式独立成块、内容级去重。
- **④ 多轮 · 上下文压缩**：history 滑窗（最近 6 轮 × 200 字）+ query 改写。
- **⑤ 生成侧 · 输出控制**：post_filter 剥离"补充说明"式编造节 + SSE 流式输出。

### Q3. 多轮对话历史会越来越长，你怎么防止它膨胀？

两招。① **滑窗截断**：只带最近 6 轮、每轮截 200 字。② 关键是 **query 改写**——我不把多轮历史直接塞进生成 prompt，而是用 LLM 把"那托儿所呢"压缩成"托儿所的服务半径要求"这一句独立检索 query。这样生成只看本轮检索到的 chunks，历史只用于"理解问题"。**一个设计同时省 token + 守"不编造"红线**（旧轮的数字不会漏进新答案）。

### Q4. 为什么不直接用长上下文模型，把整个规范库塞进去？

三个理由：
1. **token 成本**：全库估百万级 token，撑爆窗口且每次调用天价。
2. **噪声 / 编造**：召回越多越杂，模型越容易基于弱相关上下文编造——我实测过 chunks 清干净后反而更敢编造（数据质量↑ ≠ 产品质量↑）。
3. **可溯源**：RAG 才能把答案回链到具体规范条文 + 原文 PDF，这是"像查法条"产品的立身之本，长上下文直塞做不到精确引用。

### Q5. Reranker 在 context 工程里起什么作用？

它是"**用小模型省大模型 token**"。BGE-Reranker 在本地把粗排的 20 条筛到 5 条，等于用便宜的本地重排算力，换掉昂贵的 LLM context token——既提精度又省钱。粗排 Top20 保召回（recall），精排 Top5 保精度 + token 预算，是一个 recall-vs-token 的刻意权衡。

### Q6. 你的 query 改写具体怎么做、为什么算"上下文压缩"？

多轮里用户常用指代词（"那""它"）。我用 LLM 把"历史 + 本轮问题"改写成一句自包含的检索 query，**只补指代、不增信息、不回答**。它本质是上下文压缩：把可能很长的多轮历史压成一句话喂给**检索**，而不是把全历史喂给**生成**。失败兜底是回退原 query（宁可少补指代，不乱改用户问题）。

### Q7. 只喂 Top5、做 context 压缩，会不会丢关键条文？怎么保证？

会有损失风险，所以我用**评测**守住。7 维度评测里有"检索召回""精确条款"两个维度专门盯这个；Top-K 和相关度阈值不是拍脑袋定的，是在评测集上调出来的（不存在通用最佳，参数由 KPI 决定）。阈值过滤后 0 命中就触发兜底"未在现行规范库中查询到"，**宁可拒答，不基于弱相关上下文硬答**。

### Q8. chunk 怎么切的？和 context 有什么关系？

以"条"为基本分块单元、单 chunk ≤800 字、表格和公式独立成块，并保留规范号 + 条文号 + 页码元数据。这既是 **token 预算单元**（每个上下文块有界），也保证语义完整和可溯源——切碎了就无法精确引用，违"引用精确"红线。还做了内容级去重，避免冗余 chunk 白占 context。

### Q9. 如果让你继续深化 context 工程，你会做什么？

显式 token 预算（按 token 数动态决定喂几条 chunk，而非固定 5）、长对话历史摘要压缩、长 chunk 分层检索 / 摘要。**但我评估过——当前 context 规模（千级 token）够用，再加是过度工程**。我更倾向先把已有设计量化、用评测验证，而不是为了"显得复杂"堆技术。

### Q10. 一句话总结你的 context 工程理念？

不是"塞得多"，是"**喂得准**"——检索是选择、rerank 是精选、改写是压缩、评测是刹车。每一层都在 token 成本、答案质量、可溯源之间做权衡。
