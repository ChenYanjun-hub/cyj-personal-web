# 建景规 · Agentic RAG · 面试 Q&A

> 用途：AIPM 面试被问到「你做过 Agent 吗 / 怎么用 agent 优化 RAG / 多 Agent 编排」时的备答稿（第一人称，可直接复述）。
> 全部基于「建景规规范问答助手」真实落地的三个 agent，每个都有生产代码 + 评测 / 实证。
> 一句话定调：**我上 agent 的标准不是"显得复杂"，是"有证据指向的真问题 + 能用对指标验证"。三个 agent 各打一类问题，都默认关、可 flag 开。**
> 维护：2026-W7 · 配套：[评测保真 QA](评测保真-面试QA.md) · [RAG-Context 工程 QA](RAG-Context工程-面试QA.md)

### Q1. 你这个项目做了哪些 Agent？

三个，各打一类**证据指向的**问题，都是生产代码（默认关 + 环境变量 flag，可一键开）：

| Agent | 模式 | 打什么问题 |
|---|---|---|
| ① 查询分解 | 任务分解 | 发散/复合题单次检索只覆盖一个子话题（综合域最弱）|
| ② 引用核验 | Verifier / Reflection | 规则治理抓不到的语义编造（假规范号、错数字）|
| ③ 工具调用 | ReAct / function-calling | 精确查表类查询（目录导航/条文定位/现行状态）向量检索天生弱 |

### Q2. 查询分解 Agent 具体怎么做的？

LLM 先判断查询是"复合/发散"还是"单一"：单一**不拆**（零额外开销），复合才拆成 2~4 个自包含子问题，
每个子问题**各自**检索 + **各自**重排，最后合并覆盖各子话题。

一个关键细节：**重排必须对子问题打分，不能对原复合 query 打分**。我第一版接错了——
子问题结果融合后仍用原始复合 query 重排，结果期望条还是排在低位（第 9 名）；
改成子问题各自重排后，同一条直接进第 1 名。

### Q3. 分解的效果怎么样？（这题有坑，答好加分）

**在检索命中率（Hit@5）上是 0 变化——我一度以为白做。** 后来意识到：我在用错的尺子量。
retrieval Hit@5 只检查**一条**期望条在不在 top5，而分解解决的是**多个子话题的覆盖**，维度根本不同。

换成生成侧看，价值立刻显现。以"城市新区的道路建设有什么规范要求"为例：

| | 不分解 | 分解 |
|---|---|---|
| 喂给 LLM 的片段 | 5 条，全挤在"道路规划总则"一个话题 | 8 条，覆盖红线/绿化/照明/交通 4 个子话题 |
| 生成答案 | 空泛总则，无具体规定 | 逐条给出红线宽度（≤70/55/40m）、绿化、照明（≥3.5m）、通行能力，每条带规范号 |

**两版对单条 GT 都算"miss"，但分解版对用户有用得多。** 这就是"用错指标看是 0 提升，用对指标看是质变"。

### Q4. 引用核验 Agent 解决什么？和你原有的规则治理不冲突吗？

不冲突，是**分工**。我原本有一套确定性规则治理：剥"补充说明"节、校"应/宜"量词、查 `[N]` 角标越界。
但规则有边界——**"引了一个看着对但片段里根本没有的规范号"，规则抓不到**：它角标没越界、量词也没错，纯粹是语义级编造。

所以加了 LLM verifier：逐项核对答案里的规范号/条文号/数字/强制性用语是否被检索片段支持，列出无据项。
控制实验里我植入了假规范号 `GB 99999-2099`、错数字 `500m`/`2000m²`，**三处全被抓出，且对有据答案零误报**。

### Q5. 有没有真的抓到过线上问题？

有，而且是上线第一条查询就抓到了——这也是我最想讲的一个瞬间。

模型把原文「**不应**把裸灯设置在视平线上」写成了「**应把**裸灯设置在视平线上」。
**漏一个"不"字，禁止性规定变成了要求性规定，语义完全反转**——这是我定义的红线 3（强制性条文用语不可错）的硬违规。
而规则式的量词对齐**没抓到**（跨字的否定词丢失，上下文锚点匹配不上），verifier 抓到了。

这件事把"规则打高频可模式化的错、LLM 兜语义级编造"从理论变成了实证。

### Q6. 为什么 verifier 只检测不自动改写？

**因为自动改写生成文本的风险，我已经踩过一次。** 早期我做过自动对齐数字（把答案里的数字改回片段原值），
评测显示综合分 -6.7、数字维度 -19.9pp，直接回滚了。文本自动修改的 blast radius 很大。

所以 verifier 第一版只做"看见"：把无据项写进 metadata、在 UI 上显式列出来，让人判断。
**先可观测，再自动化**——等有足够数据证明 verifier 判得准，再考虑做"打回重生成"的闭环。

### Q7. 工具调用 Agent 给了它哪些工具？怎么防止乱调？

三个确定性工具（不依赖 LLM，可单测）：`list_specs`（按域列规范）、`lookup_clause`（规范号+条文号精确定位原文）、
`check_spec_status`（现行/作废）。用 DeepSeek function-calling，agent 自己判断调哪个。

**防乱调是重点**。第一版我发现"防火墙的耐火极限是多少"这种**内容类**问题也被路由去调工具了——
模型想"先列规范再查条文"，但那不是工具能答的。两处修复：
1. **prompt 里明确"内容类语义查询不调任何工具"** + 给出正反例；
2. **改成多轮 ReAct 循环，每轮都带 tools**——第一版只做两次调用，第二次没带 tools，
   模型想调第二个工具时把 tool_call 当文本吐了出来，直接泄漏成乱码。

修完后：三类查表问题正确调对工具，内容类问题**不调工具、回退常规 RAG**。

### Q8. 这些 agent 都默认开着吗？成本怎么控？

**全部默认关。** 因为每个 agent 都要额外的 LLM 调用：分解要一次判定（~1.5s）、核验要一次核对，
而多数查询是简单内容查询，给它们都加一次调用不划算，还会压我定的 TTFT ≤3s SLA。

我的下一步优化是**廉价预筛**：用正则/长度先判断"明显是单一问题"就跳过分解的 LLM 调用；
核验只对"数字/规范号密度高"或"检索相关度低"的答案触发。**先把能力做出来并验证，再谈什么时候值得付这个成本。**

### Q9. 你怎么让用户感知到这些 agent 在工作？

做了 agent 能力可见化：头部徽章 `⑂ 已拆解 4 问` / `⚒ 工具 list_specs` / `✓ 引用已核验`（或 `⚑ N 处待核`），
卡片内还会**逐条列出拆出的子问题**、**逐条列出核验发现的无据项及原因**。

理由是：对"像查法条"的产品，**过程可见就是信任基础设施**。尤其"⚑ N 处待核"——
产品**主动承认"这里我不确定"**，比假装完美更可信。
而且可见化会反向暴露问题：上面那个红线违规，如果只躺在 metadata 里没人会发现，**摆到 UI 上才被看见**。

### Q10. 做这三个 agent，最大的方法论收获是什么？

三条，都吃过亏：
1. **上 agent 前先想清楚"它改善的是哪个指标"**（分解在检索指标上 0 变化，价值在生成完整性）。
2. **别用一种手段包打天下**（规则和 LLM 核验是分工，不是替代）。
3. **先诊断再动手**。我还有一个 agent 方向做到一半停了——原本要做"国标优先重排 boost"，
   诊断发现那些国标条**根本没被召回**（在全库排 47/93 名），boost 救不了不在候选里的东西。
   **于是我没写那行代码**，把问题路由给了数据修复和评测复核。**知道何时不做，也是判断力。**
