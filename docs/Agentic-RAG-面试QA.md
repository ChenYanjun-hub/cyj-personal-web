# 建景规 · Agentic RAG · 面试 Q&A

> 用途：AIPM 面试被问到「你做过 Agent 吗 / 怎么用 agent 优化 RAG / 多 Agent 编排 / agent 怎么评测」时的备答稿（第一人称，可直接复述）。
> 全部基于「建景规规范问答助手」真实落地的**三个 agent + 一层调度 + 一套 agent 评测**，每个都有生产代码与实证数据。
> 一句话定调：**我上 agent 的标准不是"显得复杂"，是"有证据指向的真问题 + 能用对指标验证 + 成本可承受"。**
> 维护：2026-W7 · 配套：[评测保真 QA](评测保真-面试QA.md) · [RAG-Context 工程 QA](RAG-Context工程-面试QA.md)

---

### Q1. 你这个项目做了哪些 Agent？

三个 agent，各打一类**证据指向的**问题，外加一层**调度**把它们管起来：

| 层 | 模式 | 打什么问题 | 现状 |
|---|---|---|---|
| **Agent Router** | 调度 / Orchestration | 三个 agent 各自对每条 query 收 LLM 税 | **默认开**（规则 ~0ms）|
| ① 查询分解 | 任务分解 Planning | 发散/复合题单次检索只覆盖一个子话题 | **默认开**（Router 后）|
| ② 引用核验 | Verifier / Reflection | 规则治理抓不到的语义编造（假规范号/错数字）| 暂缓（有明确前置条件）|
| ③ 工具调用 | ReAct / function-calling | 精确查表类查询（目录/条文定位/现行状态）| **默认开**（Router 后）|

### Q2. 查询分解 Agent 具体怎么做的？

LLM 先判断查询是"复合/发散"还是"单一"：单一**不拆**（零额外开销），复合才拆成 2~4 个自包含子问题，
每个子问题**各自**检索 + **各自**重排，最后合并覆盖各子话题。

一个关键细节：**重排必须对子问题打分，不能对原复合 query 打分**。我第一版接错了——
子问题结果融合后仍用原始复合 query 重排，期望条还是排在低位（第 9 名）；
改成子问题各自重排后，同一条直接进第 1 名。

### Q3. 分解的效果怎么样？（这题有坑，答好加分）

**在检索命中率（Hit@5）上是 0 变化——我一度以为白做。** 后来意识到：我在用错的尺子量。
retrieval Hit@5 只检查**一条**期望条在不在 top5，而分解解决的是**多个子话题的覆盖**，维度根本不同。

换成生成侧看，价值立刻显现。以"城市新区的道路建设有什么规范要求"为例：

| | 不分解 | 分解 |
|---|---|---|
| 喂给 LLM 的片段 | 5 条，全挤在"道路规划总则"一个话题 | 8 条，覆盖红线/绿化/照明/交通 4 个子话题 |
| 生成答案 | 空泛总则，无具体规定 | 逐条给出红线宽度（≤70/55/40m）、绿化、照明（≥3.5m）、通行能力，每条带规范号 |

**两版对单条 GT 都算"miss"，但分解版对用户有用得多。** 这就是"用错指标看是 0 提升，用对指标看是质变"。

### Q4. 引用核验 Agent 解决什么？和你原有的规则治理不冲突吗？

不冲突，是**分工**。我原本有一套确定性规则治理：剥"补充说明"节、校"应/宜"量词、查 `[N]` 角标越界。
但规则有边界——**"引了一个看着对但片段里根本没有的规范号"，规则抓不到**：它角标没越界、量词也没错，纯粹是语义级编造。

所以加了 LLM verifier：逐项核对答案里的规范号/条文号/数字/强制性用语是否被检索片段支持，列出无据项。
控制实验里我植入了假规范号 `GB 99999-2099`、错数字 `500m`/`2000m²`，**三处全被抓出，且对有据答案零误报**。

### Q5. 有没有真的抓到过线上问题？

有，而且是上线第一条查询就抓到了——这也是我最想讲的一个瞬间。

模型把原文「**不应**把裸灯设置在视平线上」写成了「**应把**裸灯设置在视平线上」。
**漏一个"不"字，禁止性规定变成了要求性规定，语义完全反转**——这是我定义的红线 3（强制性条文用语不可错）的硬违规。
而规则式的量词对齐**没抓到**（跨字的否定词丢失，上下文锚点匹配不上），verifier 抓到了。

这件事把"规则打高频可模式化的错、LLM 兜语义级编造"从理论变成了实证。

### Q6. 为什么 verifier 只检测不自动改写？

**因为自动改写生成文本的风险，我已经踩过一次。** 早期我做过自动对齐数字（把答案里的数字改回片段原值），
评测显示综合分 -6.7、数字维度 -19.9pp，直接回滚了。文本自动修改的 blast radius 很大。

所以 verifier 第一版只做"看见"：把无据项写进 metadata、在 UI 上显式列出来，让人判断。
**先可观测，再自动化**——等有足够数据证明 verifier 判得准，再考虑做"打回重生成"的闭环。

### Q7. 工具调用 Agent 给了它哪些工具？怎么防止乱调？

三个确定性工具（不依赖 LLM，可单测）：`list_specs`（按域列规范）、`lookup_clause`（规范号+条文号精确定位原文）、
`check_spec_status`（现行/作废）。用 DeepSeek function-calling，agent 自己判断调哪个。

**防乱调是重点**。第一版我发现"防火墙的耐火极限是多少"这种**内容类**问题也被路由去调工具了。两处修复：
1. **prompt 明确"内容类语义查询不调任何工具"** + 给正反例；
2. **改成多轮 ReAct 循环，每轮都带 tools**——第一版只做两次调用，第二次没带 tools，
   模型想调第二个工具时把 tool_call 当文本吐了出来，直接泄漏成乱码。

### Q8. ⭐ 你怎么控制 agent 的成本？（这题最能体现工程判断）

**这是我做完三个 agent 后遇到的真问题：它们全都默认关着——不是效果不好，是成本模型不对。**
每个 agent 都对**所有** query 加一次 LLM 调用（分解判定 ~1.5s、核验 ~1.3s），
而真实流量多数是简单单点查询，根本用不上，还会压我定的 TTFT ≤3s SLA。

**这不是"agent 能力不够"，是缺一层调度。** 所以我加了 **Agent Router**：
- **廉价规则先分**（正则，48 条 query 共 **0.2ms**、零 LLM 成本）：目录问法 / 规范号+条文号 / 并列复合 / 发散措辞
- **LLM 只兜规则分不开的模糊区**（可选，默认关）
- 路由结果统一 gate 三个 agent —— **简单题走常规 RAG，一分钱 agent 成本不付**

结果：tool 和 decompose **从"没人敢开"变成默认开**。实测简单题 TTFT 553ms / 总 7.1s，完全在 SLA 内。

### Q9. ⭐ Agent 你怎么评测？

我原本有三层评测：检索层、生成层、兜底层——**唯独没有一层在问"agent 的决策对不对"**。
所以补了第四层：**agent 行为评测**。

- **测试集**：48 条手工标注（tool 12 / decompose 14 / plain 22），其中 **10 条 borderline**——
  专门是"措辞像发散、实为单点"的陷阱题（如"填方路基对填料的最大粒径有什么要求"）。
- **指标（agent 时代该定义的新 KPI）**：
  - **误触发率**：本该走常规 RAG 却调了 agent → **白付成本**
  - **漏触发率**：本该调 agent 却退回常规 RAG → **无损降级**
  - 加上每类召回/精确、混淆矩阵、clear vs borderline 分开报告

**标注纪律**：ground-truth 按**语义真实**判定，**不按"我的正则怎么走"**——
否则就是在优化一个坏掉的 KPI（我在评测保真那条线上吃过这个亏）。

结果演进（两轮**有原则的**修正，不是针对样本打补丁）：

| | 整体 | clear | 误触发 | 漏触发 |
|---|---|---|---|---|
| 初版规则 | 77.1% | 92.1% | 27.3% | 19.2% |
| **终版（默认）** | **93.8%** | **100%** | 13.6% | **0%** |
| 终版 + LLM 兜模糊区 | 95.8% | 97.4% | **4.5%** | 3.8% |

`tool` 路由全程 **100% 召回 / 100% 精确**（规范号+条文号是极强信号）。

### Q10. 那 LLM 兜模糊区效果更好，为什么不默认开？

因为**数据显示它是个权衡，不是纯赚**：它把误触发从 13.6% 降到 4.5%，
但 **clear 样本准确率从 100% 掉到 97.4%**（LLM 把"城市地下道路设计要满足哪些基本要求"判成了单点），
还引入不确定性和额外延迟。

而纯规则版：**clear 100%、漏触发 0%、0ms、确定性、可单测**。
剩下 3 条误触发全是 borderline 措辞题，**误触发的实际代价只是多花一次分解成本，答案仍然正确**——
比"发散题没拆导致答不全"轻得多。

所以我**默认纯规则，把 LLM 升级留成 flag**，等成本成为瓶颈时再开。
**用数据决定，不用"看起来更强"决定。**

### Q11. 你怎么让用户感知到这些 agent 在工作？

做了 agent 能力可见化：头部徽章 `⑂ 已拆解 4 问` / `⚒ 工具 list_specs` / `✓ 引用已核验`（或 `⚑ N 处待核`），
卡片内还会**逐条列出拆出的子问题**、**逐条列出核验发现的无据项及原因**。

理由是：对"像查法条"的产品，**过程可见就是信任基础设施**。尤其"⚑ N 处待核"——
产品**主动承认"这里我不确定"**，比假装完美更可信。
而且可见化会反向暴露问题：Q5 那个红线违规，如果只躺在 metadata 里没人会发现，**摆到 UI 上才被看见**。

### Q12. 做这一整套，最大的方法论收获是什么？

四条，都吃过亏：
1. **上 agent 前先想清楚"它改善的是哪个指标"**（分解在检索指标上 0 变化，价值在生成完整性）。
2. **别用一种手段包打天下**（规则治理和 LLM 核验是分工，不是替代）。
3. **能力 ≠ 可上线。agent 的瓶颈常在调度，不在能力**——
   我做完三个 agent 才发现它们全关着，加了一层 0ms 的路由才真正上线。
   Router 的价值不是提升单条答案质量，是**让已有能力的成本变得可承受**。
4. **先诊断再动手**。我还有一个 agent 方向做到一半停了——原本要做"国标优先重排 boost"，
   诊断发现那些国标条**根本没被召回**（在全库排 47/93 名），boost 救不了不在候选里的东西。
   **于是我没写那行代码**，把问题路由给了数据修复和评测复核。**知道何时不做，也是判断力。**
