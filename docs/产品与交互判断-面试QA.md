# 建景规 · 产品与交互判断 · 面试 Q&A

> 用途：AIPM 面试被问到「你做过什么产品决策 / 怎么做交互设计 / 怎么把技术能力变成用户价值」时的备答稿（第一人称，可直接复述）。
> 前三份材料讲的是**技术怎么做**，这份讲的是**产品怎么判断**——对 AIPM 岗位这条往往更关键。
> 一句话定调：**我做界面不是"照着设计稿实现"，是先问"这个视觉需要什么数据支撑、它承载了哪条产品红线"。**
> 维护：2026-W7 · 配套：[评测保真 QA](评测保真-面试QA.md) · [Agentic RAG QA](Agentic-RAG-面试QA.md) · [RAG-Context 工程 QA](RAG-Context工程-面试QA.md)

### Q1. 你在这个项目里做过哪些产品决策？举最能体现判断力的。

五个，都有明确的取舍理由（不是"设计稿画了我就做"）：

| 决策 | 判断 |
|---|---|
| **强制性用语分级高亮** | 把红线做成**用户看得见的** |
| **项目工作区 = 预设规范范围** | 不做成"会话文件夹"，而是接到已有检索能力上 |
| **导出报告** | 把"可追溯"从体验变成**可交付物** |
| **公式块渲染 → 决定不做** | 诊断发现数据支撑不了，改做守卫 |
| 上传图纸查合规 → **砍掉** | 直接撞"不下合规结论"红线 |

### Q2. 强制性用语高亮，为什么说它是"产品决策"而不是美化？

因为它对应我定的**红线 3：强制性条文用语不可错**（"应/不应" vs "宜/不宜" vs "可/不可"，法律效力完全不同）。
规范圈里最容易出事的就是把"宜"当成"应"执行、或反过来。

所以我做的不是"高亮关键词"，是**按法律效力分三档**：
强制（必须/严禁/不应/不得/应）红色 · 推荐（宜/不宜）琥珀 · 允许（不可）灰色，鼠标悬停给出解释。
**用户一眼就能看出这条是"必须"还是"建议"**——这是查法条类产品的核心可用性。

一个实现细节能体现严谨度：单字"应/宜"是常用字，直接高亮会把"**应**用""响**应**""**宜**居""适**宜**"误标成强条用语。
我加了上下文守卫；单字"可"直接不高亮（"可以/可能/认可"误报率太高，且法律效力最弱）。
而且这套量词定义**复用后端后处理模块的同一份清单**，避免前后端各写一套、日后漂移。

### Q3. ⭐ 这个高亮功能上线后，有没有意外发现？

有，而且是我最想讲的一件事：**高亮一上线，当场照出一个潜伏已久的 bug。**

我看到琥珀色的「宜」出现在一个奇怪的位置——用户问的是"服务半径**不应**大于多少米"，
但答案里复述这个问题时变成了"服务半径**宜**大于多少米"。**产品把用户的提问改写了**，读起来像助手听错了问题。

根因是我早先做的一个后处理规则：它会把答案里的量词按规范原文校正（这是为守红线 3 而做的）。
但它**没有"作用域"概念**——把答案里"复述用户问题"的那句也一起改了。
**为守红线而生的组件，在错误语境下自己制造了那类错误。**

这件事有两个收获：
1. **可见化会反向暴露问题**。这个 bug 一直存在，只是没有高亮时没人会注意到那个"宜"字不对劲。
   **观测性做在 UI 上，bug 才会被看见。**
2. **定义自动化规则时，必须同时定义它的作用域**——"改什么"和"在哪里不改"同样重要。

### Q4. 那个 bug 你怎么修的？（这题的重点在"第二次风险"）

思路是给那个后处理传入用户的原始问题，**保护"答案中引述该问题"的片段不被改**（只缩小作用域，不扩大）。
判定用双条件：在**引号内** + 与用户问题**高度相似**。单看任一条都不行——
只看相似度会误伤"恰好与提问用词相同的规范陈述"，只看引号会误伤"引用规范原文"（那些恰恰**需要**被校正）。

**关键在这儿**：我第一版相似度阈值取 0.6，看着修好了。但我按纪律去量影响面——
在 1802 条存档评测答案上跑，发现 **4.4% 受影响**，逐条看才发现**多数不是"引述提问"，而是"引用规范原文"**
（提问本就围绕那条条文，用词自然重合）。如果答案在引号里**误引**了原文，那正是红线该校正的，
我的守卫会把它挡住——**修一个 bug，造出 13 个更危险的漏洞。**

改用数据定阈值：14 条候选的相似度分布有干净断层（真·引述提问 0.98 / 引用规范原文 ≤0.79），
取 **0.90** 切在断层上。方向上**宁可漏保护、不可误保护**（误保护会拦下红线校正=有害；漏保护只是退回原行为=无新增伤害）。

**金句**：*"我修一个后处理 bug 时，第一版阈值差点让它挡住 13 条合法的红线校正——
我是在 1802 条存档答案上量了影响面，才发现分布有个干净断层，把阈值定在那里。"*

### Q5. 项目工作区，你为什么说它不只是"会话分组"？

如果只做成文件夹，它就是个视图功能，价值有限。但规划师的真实痛点是：

> 同一个"日照间距怎么算"，在深圳要叠深圳地标 + IV 气候区系数，在哈尔滨完全是另一套。

所以我把项目定义为 **会话分组 + 预设规范范围**。后者直接复用了我早先做的"多选规范限定检索"能力——
**零后端改动，但两个功能互相放大**：多选限定有了"记忆"，项目有了"实质作用"（它改变**检索行为**，不只是改变视图）。

**判断一个功能是不是"真功能"，看它有没有改变系统行为。** 分组只改变视图；预设规范范围改变了检索。

三条设计取舍都为了不夺走用户控制权：
① **手动选了规范就用手动的**，没选才用项目预设（否则用户会"取消不掉"）；
② **删项目不删会话**（用户的问答历史比分组更宝贵）；
③ 选中项目 = 进入该项目上下文（历史列表只显示该项目会话）。

### Q6. ⭐ 有没有哪个界面功能，你诊断后决定不做？

有——**公式块渲染**。设计稿里有个很漂亮的公式块（`L = H · i` 加变量图例），我动手前先查了语料：

- **10785 条 chunk 里只有 1 条是公式类型**，而且那一条也是 OCR 垃圾
- 混在正文里的公式**全是坏的**：`AADT= (4.5.4)`（等号右侧整段丢失）、
  `E-B2FK×100% C=`（字符顺序错乱）、`PQI=T×am×RQI+RCIXa`（变量被错认）

**渲染一个损坏的公式，等于把乱码包装得像模像样**——用户会以为那是准确公式，
这比不渲染更危险，直接违"不编造 / 引用精确"两条红线。

所以我不做渲染，改做**诚实的守卫**：含公式的条文打「含公式·查原文」标记，引导用户核对原文 PDF，
并且**导出报告里同步标注**（否则交付物就丢了这条风险提示）。检测信号取保守口径，
实测命中 1.01%、抽样零误报。

**实测恰好印证了必要性**：有一条 chunk 原文是乱码 `1 ×No1-4.98-0.34×R1`，
但模型答案给出了干净的 `RQI = 4.98 - 0.34 × IRI`——**它从乱码里"重构"了公式**。
这次看着合理，但它同样可能自信地重构出一个错的。守卫就是针对这个。

### Q7. Q6 这个决策，你会怎么概括成方法论？

**设计稿画的是理想数据。视觉可以先行，但上线前必须回答"这个视觉需要什么数据支撑，我有吗"。**

还有一层更反直觉的：**呈现越精致，对数据质量的要求越高**。
同样一段 OCR 乱码，用纯文本显示时用户能看出不对劲；排进精美的公式块，反而显得权威。
**渲染质量会放大数据质量的欺骗性。**

### Q8. 导出报告，你怎么决定报告里放什么？

**报告里最重要的不是答案**（那能复制粘贴），**是依据的可追溯性**——
规划师要把结论放进设计说明，审图时必须能指回"这条依据是哪部规范第几条第几页、现在还有没有效"。

所以引用清单里：规范全称 + 标准号 + 条文号 + 页码 + 强制性标记 + 现行状态 + **原文摘引**，一个都不能少。
审图人看的是原文，不是 AI 的转述。

三处红线相关的设计：
1. **含非现行规范时显式告警**（条目内标"⚠️ 已废止，现行替代 XXX"，并在轮末汇总）——审图会看这个；
2. **免责声明必带**（"不构成合规结论，请咨询规划主管部门或专业审图机构"）——对应"不下合规结论"红线；
3. **自动核验发现的待核项一并导出**——那是风险信息，不能只留在界面上。

格式选 Markdown 而不是 Word/PDF：零新增依赖、可直接粘进 Word/飞书。
Word/PDF 需要引第三方库，属于"要先请示"的决策，我没有自己拍。

### Q9. 你引入过新的第三方库吗？怎么决策的？

引过一次：答案的 Markdown 渲染（`react-markdown` + `remark-gfm`）。
起因是工具类回答常带表格，纯文本渲染会显示成 `| 序号 | 规范号 |` 的原始管道符，很不专业。

**决策纪律**：项目规范写明"引入新库必须先请示"，所以我先说明代价（bundle 从 70KB 涨到 116KB gzip）、
给出备选（手写 mini 解析器，零依赖但表格/嵌套易错、维护成本更高），由负责人拍板后才装。

**这次改造最需要小心的地方不是排版**：正文里的 `[N]` 引用角标是"每条事实可回链到规范条文"的唯一入口（红线：可追溯）。
Markdown 渲染会把文本拆成 AST 节点，**无脑替换就会把角标吃掉——排版变好了、可追溯性没了，净损失。**
所以我给渲染器的每个含文本元素都套了一层处理，把角标还原成可点击的 chip。

验收标准也因此不是"好看了"，而是"好看了**且**原有关键交互一个不少"：
我实际点了一次角标，断言它仍能高亮联动——**可见 ≠ 可用，验收要测交互，不能只截图。**

### Q10. 一句话总结你的产品判断方法？

**先问这三个问题，再动手做界面**：
1. 这个视觉**需要什么数据支撑**，我有吗？（→ 公式渲染决定不做）
2. 这一层里**哪些交互承载了产品红线**，改造时会不会弄丢？（→ Markdown 渲染保住引用角标）
3. 这个功能**改变了系统行为，还是只改变了视图**？（→ 项目工作区做成预设规范范围）
