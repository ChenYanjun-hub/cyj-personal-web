# 建景规 · 评测保真 · 面试 Q&A

> 用途：AIPM 面试时被问到「你怎么优化 RAG 效果 / 怎么做评测 / 准确率怎么提上去的」时的备答稿（第一人称，可直接复述）。
> 全部基于「建景规规范问答助手」一次真实的优化推进：**strict Hit@5 从 78.8% 提到 89.8%，一行检索代码没改——全部来自把评测修准。**
> 一句话定调：**很多"模型不够好"其实是"评测不够准"。我先证明了"提升空间"里大部分是评测自己标错的，剩下的才是真问题。**
> 维护：2026-W7 · 对应召回优化推进线（启示 78/79/80/81）。配套：[RAG-Context 工程 QA](RAG-Context工程-面试QA.md)。

### Q1. 你这个项目做过什么检索优化？效果怎么样？

我做的最有价值的一次"优化"，结论是**基本没动检索、动的是评测**——strict Hit@5 从 78.8% 提到 89.8%（+11pp），检索代码零改动。
这不是取巧：我先给检索建了可信基线，逐条审计失败案例，发现那看似 20pp 的"优化空间"里，大部分是**评测集自己把答案标错了**——检索本来就对，是 KPI 在骗人。

（三层：GT 校准 +6.6pp、多值口径升级 +4.4pp，最后诊断证明残余检索失败无可行代码杠杆，刻意不改。）

### Q2. "评测保真"是什么？为什么优化前先做它？

**KPI 驱动优化的前提是 KPI 可信。** 评测集是人写的，会错——标错条文号、答案标得不精准、一个问题多个合法答案却只认一个。
如果不先校验就直接优化模型，会掉进最危险的陷阱：**把模型硬调向那些错误的标准答案，结果产品变差、分数变好。**
所以我的第一步永远是：拿到一个"不好看的指标"，先打开 badcase 看指标本身对不对，再谈优化。

### Q3. 你具体怎么发现评测标错的？

**逐条读原文对比。** 我把 29 条"检索失败"的题，逐条拉出「评测认定的期望条原文 vs 检索返回的 top1 原文」。
典型：问"什么是防火分区"，评测标的期望条 3.3.1 其实是**防火间距**，而检索返回的 4.1.2 才真的是**防火分区划分**——检索对，评测错。
抽查前 4 条定义类失败，**4/4 都是评测标错**。判定依据全是可引用的原文，不是主观印象。

### Q4. 你把评测答案改成检索返回的——这不就是"把 GT 迁就模型"作弊吗？

**关键区别：我改的是"正确答案"，不是"模型返回的答案"。** 每条修正我都引原文证明：原期望条内容**明显不对题**，新条内容**明显对题**——它恰好是检索返回的，只是印证了检索本来就对。
纪律有三条：① 只改原文核验过的；② 不覆盖原集，产出新版本 + 逐条证据变更日志（可审计、可复述）；③ 模糊的、找不到干净正解的，一律标"待人工复核"，绝不硬改。

### Q5. 什么是"多值 GT"？为什么要做？

规范体系里同一主题常散在多部规范，多部都合法。比如"幼儿园服务半径"，主 GT 标了居住区标准 GB50180，但**托幼建筑设计标准 JGJ39 才直接写"服务半径宜 300~500m"**——检索返回 JGJ39 被判"错"，其实它是更直接的答案。
**单值 GT 隐含"每题只有一个正确出处"的假设，这对规范问答不成立。** 我给这类题加了"可接受的备选出处"（`also_accept`），任一命中即算命中。这不是工程细节，是"什么算答对"的产品定义。

### Q6. 你怎么区分"召回失败"和"重排失败"？为什么重要？

**这是两种病因完全不同的病，解法相反：**
- **重排失败**：目标在候选集里，但被重排挤下去 → 调 rerank / boost 有救。
- **召回失败**：目标压根没进候选集 → 调重排全白搭，得动 embedding / query 改写 / 数据质量。

诊断方法：追踪目标 chunk 在「粗排 top-K → 重排 top-K → 深排全库」的位置，一眼分辨。
**打错层，方案再漂亮也没用。**

### Q7. 最后你为什么决定"不优化检索"？这不是没做事吗？

我本来准备做"国标优先重排 boost"（地标挤掉国标的问题）。但诊断发现：**那些国标条根本没被召回**（在全库排第 47、93 名），
**boost 救不了一个不在候选里的东西**。残余失败要么是召回层（embedding 盲区）、要么是数据（OCR 乱码）、要么是评测 GT 可疑——都不是重排能救的。
**硬写一个 boost 去凑，是"为了显得在优化而优化"。** 我把问题正确路由给了数据修复线和评测复核。**"知道何时不优化"本身是工程判断力。**

### Q8. 这套方法论体现了什么 AIPM 能力？

- **评测体系是产品的方向盘**：AIPM 对"不确定输出"做产品化，第一件事是建可信评测，而不是堆功能/堆技巧。
- **数据结构即产品决策**："单值 vs 多值 GT"该由懂业务的人定，不是工程细节。
- **反直觉时先怀疑工具**：我审计到一半发现自己的脚本有 bug（复合条文号被漏判成"数据缺失"），复核后改判——**审计工具本身也要被审计**，留下自查纠错的痕迹本身是可信度证据。
- **克制**：多个通用检索杠杆（multi-query / hybrid）此前已用评测证伪下线，我没有为了"显得复杂"重新堆上去。

### Q9. strict / loose / MRR 这些指标你怎么理解？

- **Hit@5 loose**：top5 里有没有命中对的**规范**（spec 级召回）。
- **Hit@5 strict**：top5 里有没有命中对的**具体条文**（spec + clause）。两者的差，就是"规范找对了但条文排错"的量。
- **MRR**：命中位置的倒数均值——不只看"中没中"，还看"排多靠前"。
本项目 loose 一直 91%+，说明找对规范没问题；strict 和 loose 的差，才是审计要盯的地方——而它里面很大一块是评测标注错。

### Q10. 一句话总结你的方法论？

**先修评测，再谈优化模型。** 指标不可信时，调模型是在给一个坏掉的尺子做校准——越努力越偏。
我这次最有价值的产出，一个是 +11pp 的真实提升，另一个是一行检索代码没改——**后者更能证明产品判断力。**

### Q11. ⭐ 你手上有一份缺陷清单，你会直接照着修吗？

**不会。我照单开工的第一件事是复核，结果第一条就是误报。**

清单把两条术语（公园绿地 / 绿地率的定义）列为「P0 · 直接毁答案」，说正文 OCR 毁成 `public parl R`。
我复核发现：**乱码的是 `type=appendix` 的中英文索引页 chunk**，正文 chunk 完好（75 字、中文占比 0.67、定义完整）。
索引页本来就只有「术语 + 页码」，短、中文占比低是**正确的数据，不是缺陷**——
原扫描口径（长度 <12 字 或 中文占比 <0.12）把索引和正文混着看了。

**决定性验证是端到端问一遍**：「什么是公园绿地」「绿地率和绿化覆盖率的区别」两题都答对、引对条文。

这两条本来要"重新 OCR PDF 页 + 重新分块入库"。**用静态特征（长度、中文占比）判缺陷会误报；
判定缺陷必须端到端跑一遍。**

### Q12. ⭐ 那你实际修了什么？效果如何？（这题我会讲一个"没涨指标"的修复）

真正的大缺陷是**清单里没写的**：住建部 PDF 页脚水印「住房城乡建设部信息公开 / 浏览专用」
被 OCR 当正文抓进 chunk——**污染 1212/10785 条（11.2%）、42 部规范**，
其中 **928 条落在用户可见的引用卡原文摘引里**。用户查"道路养护设备配备"，
引用卡上会显示 `…专业养护技术人员。` + `4 住房城乡建设部信息公开 浏览专用`。
对一个主打「像查法条一样、原文可追溯」的产品，**引用的条文里混水印本身就是缺陷**。

**但效果度量否掉了我动工时的两个理由，我照实记录**：

| 我的假设 | 实测 |
|---|---|
| 清掉噪声会提升检索 | strict Hit@5 **89.78% → 89.78%，完全不变** |
| 断句会让 LLM 引错原文（红线 3） | A/B（同 query、temperature=0）：**两版都正确引出「均应符合消防安全要求」，风险未发生** |

**已证实收益 = 928 条原文摘引变干净 + prompt 噪声字符 -1.21%，不是准确率提升。**

**我会保留这次修复，但按实测口径报收益。** 产品定位是「可追溯原文」，
引用里混水印就是缺陷，不需要靠 KPI 提升给它找理由。**"该修"和"修了会涨指标"是两件事。**

### Q13. MRR 掉了 1.5pp，你为什么说不是回退？

修复后 4 条 query 从 rank1 掉到 rank2，**0 条变好**——单看像回退。查下去不是：

- rerank 分数在 **0.99+ 饱和区**，这 4 条的分差只有 **0.0002~0.0092**
- **3/4 是同规范相邻条文互换**（内容仍对题），第 4 条换成了 GB 55037 的**更新版**同主题条文
- Hit@5 完全不变，说明召回集合没变，只是饱和区内部排序抖了一下

**结论：饱和区的 top-1 排序本身不稳定，不足以据此接受或否决一次改动。**
这和 Q6「区分召回失败 vs 重排失败」是同一个思路——**先判断指标在这个区间还测不测得准，再解读它的涨跌。**
