# 第一部分 · 项目题（对应《面试内容梳理》§3）

## 1.1 介绍你最满意的一个项目（3 min 逐字稿）

**【背景 + 目标】**
设计规范体系非常庞大（2000+ 部），规划师日均要花 1–2 小时翻 PDF 查规范，效率低、还容易错。更要命的是：通用大模型查规范会**编造规范号、条文号、数字**——而这是个"像查法条一样"低容错的场景，编造就等于不可用。所以我立项做一款面向中型设计院规划师的 RAG 规范问答产品：用自然语言查规划/建筑/景观/消防/结构/市政 6 类规范，**每条回答都必须附可追溯的规范号、条文号和原文跳转**。

**【产品架构 · 一句话串流程】**
用户提问 → 场景识别 / 边界兜底 → BGE-M3 向量检索 Top20 → BGE-Reranker 重排 Top5 → 相关度阈值过滤 → DeepSeek 流式生成 → **后处理对齐**（校正量词/数字、剥离编造内容）→ SSE 推送答案 + 结构化引用卡 + 原文跳转。

**【我负责的工作（概述 3 句）】**
我是产品负责人：① 定义问题与边界、定 4 条产品红线；② 和"AI 研发"一起定 RAG 技术栈与分块/检索/重排策略阈值；③ 设计 7 维度评测 + 一票否决 + 方差分析，把红线做成可检测的工程后处理，并每轮看数据决定上线/回滚/砍功能。

**【成果（量化）】**
综合质量分从 86.6 迭代到 90.3（首破 90），单次一票否决从 38 砍到 13；条文级检索 Hit@5 从 78.8% 提到 89.8%——**而且是零检索代码改动，靠审计出评测集自身的标注错误做到的**；语料从 39 部扩到 89 部 / 6 域 / 10785 chunks；并沉淀了 87 条可迁移的 AI 产品方法论。

**【为什么满意（1 句）】**
因为它把"AI 到底靠不靠谱"这种听起来很玄的问题，落成了**可检测、可拦截、可度量**的产品与工程——这正是 AIPM 的核心价值。

## 1.2 项目中你承担了什么角色

产品负责人 + 决策者，AI 辅助实现。具体工作内容：
- **需求/业务**：用户调研、需求分析、业务梳理（6 类规范的场景矩阵）。
- **理想态定义**：定义每类场景"理想的回答长什么样"（结论先行、溯源完整、强条标识）。
- **评测体系构建**：7 维度评测 + 一票否决 + 方差分析。
- **架构设计**：与 AI 研发一起定技术栈与关键阈值（不是甩给研发，是共担决策）。
- **策略调优**：发现 badcase → 拆解 → 定位根因 → 给优化方案 → 验收。

> 诚实补充：本项目没有真实的算法/前后端团队，"研发/算法"角色由 AI 承担，我做"定义 + 审校 + 决策"。真正的**多角色团队协作**故事建议用**云上米轨**或工作经历来讲（见 §1.7、§2.5）。

## 1.3 项目的核心价值

- **用户价值**：把"查不到 / 看不懂 / 不敢用"三大痛点，变成"问一句就给答案 + 给原文 + 标强制性"，且**敢用于专业判断**（因为可溯源、不编造）。
- **产品差异化价值**：市场上"AI 智能 × 规范权威 × 可溯源跳转"三者的交集是空白——通用 LLM 会编造、规范电子版只能检索、垂类工具不深耕规范问答。我占的就是这个交集。
- **方法论价值**：沉淀了一套"红线工程化 + 评测先于优化"的可迁移打法。

## 1.4 算法指标 & 业务指标

**算法指标（先验 / 离线评估，有真实数据）**
- 检索层：Hit Rate@5、Recall@K、MRR、NDCG@K（目标 Hit Rate@5 ≥ 80%）。
- 生成层：7 维度 LLM Judge MOS 打分（0/1/2 三分制）+ 3 个红线维度的**一票否决（veto）召回**。
- 实际数据：综合分 86.6 → 88.3 → **90.3**；单次 veto 38 → 27 → **13**；dim4 原文用词准确率 86.2% → **94%**。

**业务指标（诚实口径）**
- 设计的衡量框架是：使用人数、用户满意度、规范查找效率（替代"翻 PDF 1–2 小时"）。
- **但本项目是 MVP / 作品集项目，未规模化上线，没有真实业务数据。** 面试如实说：业务指标是我**设计好的度量框架与目标值**，落地后才能采集。我能讲清楚"为什么这么定指标"，而不是编一个使用量。

## 1.5 有复盘吗？哪些可以提升

**产品侧**
- 业务侧验证缺位：MVP 只到离线评测，缺真实用户的在线行为数据闭环。
- 复杂场景（条文对比 ④、计算辅助 ⑤）属 V2/V3，MVP 只覆盖了 87% 高频流量。

**落地侧**
- 评测集 vs 真实场景仍有偏差（早期评测集偏理想化，后来才补对抗陷阱样本）。
- 调优时一度过度投入策略调参，**忽视了模型选型**这条更上游的杠杆。
- 上游数据是天花板：OCR 损伤的语料限制了上限，数据清洗不可能一次彻底。

> 复盘金句：**"绿色仪表盘可能只是没测到"**——指标全绿不等于没问题，可能是评测没覆盖到。

## 1.6 项目中遇到什么困难？如何解决（STAR）

**S/T**：通用 LLM 查规范会编造；且评测分本身有噪声、语料有 OCR 损伤——"改了感觉好了"根本不可信。

**A（三招）**
1. **红线工程化**：把"不编造/用词/数字"做成可检测的后处理——`post_filter` 剥离"补充说明"式编造、`align_modal_verbs` 校正"应/宜"、`align_numbers` 校回数字、dangling 引用监控。不靠 prompt 祈祷。
2. **噪声治理**：单次 LLM Judge 约一半是噪声，用**三次交集 + 方差分析**剥离判官噪声，才认定"真问题"。
3. **OCR 清洗**：把错字分"系统性 vs 随机弥散"，字典扩充靠"占用次数 + 上下文边界验证"——8 个候选过验证只留 2 个（淘汰 75%），避免误改合法字。

**R**：综合分稳定破 90，veto 砍到 13，红线类错误工程可控；并沉淀出"上游数据是天花板""数据干净≠产品更好"等方法论。

> **反直觉发现（高频追问弹药）**：我把 chunks 的 OCR 修干净后，**编造类错误反而上升**——干净文本让模型"更自信地发挥"。结论：数据质量↑ ≠ 产品质量↑，红线得靠工程兜底。

## 1.7 与算法、研发协作遇到的问题？如何解决

**诚实口径（必须先讲清）**：本项目是我独立主导 + AI 辅助，没有真实算法/研发同事。所以这题我分两层答：

**(a) 与 AI 的"协作"分工**：我定义问题、定方案、定验收、卡红线、做迭代决策；AI 负责实现与草稿。关键是我**能判断 AI 产出对不对、敢温柔挑战它的结论**——比如 AI 给的 align_numbers 方案（启示 62）我跑评测发现反而劣化，就果断关掉。AI 草稿 + 人审是不可分割的。

**(b) 可迁移到真实团队的协作原则**（也是我在云上米轨/工作中的做法）：一开始不懂技术方案不要硬装，自学补齐 → 针对某次 badcase 能清楚定位根因并给出方案、让研发/算法认可 → 之后才能持续平等地参与技术讨论。冲突时：控制情绪、聚焦问题、摆数据讲道理、必要时向上沟通找支持（详见 §2.5）。

## 1.8 怎么做竞品调研？对比竞品有哪些优势

**方法（4 步）**
1. **定目标**：这次竞品调研要回答"市场有没有人把'规范问答'做好"——聚焦效果与差异化空间。
2. **定竞品**：直接竞品（垂类规范工具）、间接竞品（通用 LLM、规范电子版、设计院内部 KB）。
3. **展开调研**：建对比矩阵，按"优势/不足"逐类拆。
4. **梳理结论**：找差异化空白。

**对比矩阵（实测结论）**

| 类型 | 代表 | 优势 | 不足 |
|---|---|---|---|
| 通用 LLM | ChatGPT/Claude/文心 | 通用强 | 不专、**易编造、无溯源** |
| 规范电子版 | 建工出版社/知圈 | 权威 | 只能文档检索、无智能问答 |
| 建筑垂类工具 | BIMBOX/品茗 | 行业熟 | 偏施工/造价，不深耕规范问答 |
| 院内 KB | 自建 wiki | 贴合项目 | 维护成本高、检索弱 |

**我的优势 / 差异化定位**：**AI 智能 × 规范权威 × 可溯源跳转** 三者交集——通用 LLM 缺权威与溯源，电子版缺智能，垂类缺深耕。这个交集是空白，就是我的位置。

# 第二部分 · 项目梳理（对应《面试内容梳理》§4）

## 2.1 用户调研

**如何确定用户**：从需求来源（行业数字化转型 + 规范体系庞大 + 我自己的规划专业背景）出发，锁定**中型设计院规划师**——专业、低容错、要可追溯依据；MVP 进一步聚焦"规划"方向（查询频次最高）。

**调研方式**

| 方法 | 对象 | 目的 |
|---|---|---|
| 深度访谈 | 1–10 年经验规划师 | 梳理痛点、了解场景 |
| 行为观察 | 真实查询过程 | 挖隐性需求 |
| 问卷调研 | 设计院从业者 | 验证痛点普遍性 |

**用户画像（虚构代表"王工"）**：设计院规划师，3 年经验，做控规/修详规/住区方案；每天花 1–2 小时查规范；用过 ChatGPT 但**不敢用于专业判断**；核心诉求＝**答案准确 + 能看原文 + 不编造**。

**痛点 3 大类**：① 查不到（不记得规范号、搜不到条文）② 看不懂（用词专业、不知强制还是推荐）③ 不敢用（LLM 看起来对但不敢信）。

**调研→产品的转化**：怕编造 → 评测设 2 项一票否决；要看原文 → 引用溯源 + 原文跳转必做；强条易遗漏 → 红线区分"应/宜/可"。

> 详版见建景规 repo `docs/PRD.md` 第〇部分·三《用户调研》。

## 2.2 竞品调研

见 §1.8（方法 + 矩阵 + 差异化）。一句话：**三者交集（AI×权威×溯源）是空白，就是我占的位**。详版见 `docs/PRD.md` 第〇部分·二《竞品调研》。

## 2.3 技术方案

**为什么选这套方案**

| 选型 | 选择 | 为什么 |
|---|---|---|
| 技术范式 | RAG | 规范是"有标准答案、要溯源"的知识库场景，RAG 比微调更可控、可溯源、可更新 |
| LLM | DeepSeek | 成本/中文/够用；该场景不需顶尖推理，需"听话不乱编、能被提示词约束"。**不为'看起来更强'换 GPT-4** |
| Embedding/Rerank | BGE-M3 / BGE-Reranker-v2 | 中文规范语义强、本地可控 |
| 向量库 | Qdrant（本地文件） | 轻量、带 payload 过滤（domain/spec_code）|
| 后端/前端 | FastAPI + SSE / React+TS+Vite+zustand | 流式、类型安全、轻状态 |

**守红线的工程手段**（方案的灵魂）：post_filter 剥离编造、align_modal_verbs 校正用词、align_numbers 校正数字、dangling 引用监控。

**当前方案的问题 / 可改进**：
- 优点：可溯源、可更新、红线可工程拦截、技术栈锁定不追新。
- 问题：上游数据（OCR）是天花板；复杂推理（条文对比/计算）MVP 未覆盖；检索召回仍是主要提升空间（曾试 BM25 混检索失败，见 §2.4）。

## 2.4 策略调优

**遇到的问题**：① 答案编造；② 评测分有噪声、不可信；③ 数据有 OCR 损伤。

**方法 + 效果**（见 §1.6 STAR）：后处理三件套（编造/用词/数字）→ dim4 原文用词 86.2%→94%、veto 38→13、综合分→90.3。

**失败实验的科学处置（加分项）**：BM25 混检索（启示 21）、few-shot 反例治编造（启示 58）、align_numbers（启示 62 修正 60）等多个失败实验，一律 **"保留代码 + 默认关 env flag + 文档解释原因"**——失败是资产不是垃圾，且能区分"诊断假设 ≠ 改造假设"。

**有没有更好的方案**：上游——补质量更高的语料 / 更强的 OCR 后校；检索——继续打磨召回（混检索方向需重新设计而非简单加权）；选型——把"模型选型"这条上游杠杆纳入下一轮（之前过度调参忽视了它）。

## 2.5 沟通协作

**本项目实情**：独立 + AI 辅助，无真实跨职能团队（见 §1.7）。**真实协作故事用云上米轨/工作经历讲**，方法论如下：

**遇到的问题类型**：跟算法/研发意见不合、技术方案一开始看不懂、决策推不动。

**怎么解决（4 步法，面试通用模板）**：
1. **控制情绪，聚焦问题**——对事不对人。
2. **摆事实（摆数据），讲道理**——用 badcase 数据和评测结果说话，而不是"我觉得"。
3. **向上沟通，寻找支持**——决策僵持时把信息透明给上级，让有权者拍板。
4. **自学补位建立信任**——不懂技术先自学，能精准定位一次根因、让研发认可，后续才有平等对话权。

## 3.1 评测保真：我做过最有价值的"优化"，是没改模型

准备优化检索时，我先建可信基线，再逐条打开 29 例失败案例，读「评测认定的期望条原文」vs
「实际召回的原文」。结果：**约 1/3 是评测集自己标错了**——检索本来就对。
典型：问"什么是防火分区"，评测标的期望条其实是"防火间距"，而检索返回的才是"防火分区划分"。

处置：① 校准 10 条标注错误（不覆盖原集、逐条留证据）；② 引入**多值 GT**（幼儿园服务半径
GB50180 与 JGJ39 都合法，不能只认一个）。结果 **strict Hit@5 78.8% → 89.8%，零检索代码改动**。

**金句**：*"我没有优化一个坏掉的指标——我先证明了'提升空间'里大部分是评测自己标错的，剩下的才是真问题。"*

配套细节：我还自查出**审计脚本本身的 bug**（复合条文号被前缀匹配漏判成"数据缺失"），
复核后改判——**审计工具本身也要被审计**。

## 3.2 Agent 线：三个 Agent + 一层调度 + 一套 Agent 评测

| 层 | 打什么问题 | 关键实证 |
|---|---|---|
| **Router**（默认开） | 三个 Agent 各自对每条 query 收 LLM 税，导致全都"不敢开" | 规则路由 48 条 query 共 **0.2ms**、零成本 |
| 查询分解（默认开） | 发散/复合题单次检索只覆盖一个子话题 | 检索指标 0 变化，但喂给模型的片段从 1 个子话题→4 个 |
| 引用核验（暂缓） | 规则治理抓不到的语义编造 | **上线首条 query 即抓到红线违规**（见下）|
| 工具调用（默认开） | 精确查表类查询向量检索天生弱 | Router 对该类判定 **100% 召回 / 100% 精确** |

**最强的一个故事（3.2 必讲）**：模型把原文「**不应**把裸灯设置在视平线上」写成了「**应把**」——
漏一个"不"字，禁止性规定变成要求性规定，**语义完全反转**，正是我定义的红线 3 的硬违规。
规则式量词对齐**没抓到**，LLM verifier 抓到了。这把"规则打高频可模式化的错、LLM 兜语义级编造"
从理论变成了实证。

**Agent 评测（新 KPI）**：我原有检索/生成/兜底三层评测，唯独没评"Agent 决策对不对"。
新建 48 题路由评测集（含 10 题"措辞像发散实为单点"对抗样本），定义 **误触发率**（白付成本）
与 **漏触发率**（无损降级）。终版：准确率 93.8%、clear 样本 **100%**、漏触发 **0%**。

**一个克制的决策**：LLM 兜模糊区能把误触发 13.6%→4.5%，但 clear 样本从 100% 掉到 97.4%
且引入不确定性 → **默认保持纯规则，LLM 升级留 flag**。用数据决定，不用"看起来更强"决定。

## 3.3 追问：为什么有个 Agent 方向你做到一半停了？

原本要做"国标优先重排 boost"（解决地方标准挤掉国标）。诊断发现：那些国标条**根本没有被召回**

于是我没写那行代码，把问题正确路由给了数据修复线（OCR 乱码）和评测复核。

# 附录 A · 高频追问弹药（数字分身/我可直接答）

- **Q：怎么保证 AI 不乱编规范？** 双层：检索层只让答案 grounded 在召回的真实条文；生成后用后处理拦截——剥离"补充说明"式编造、把被改写的"应/宜"和数字校回原文、监控越界引用；查不到就诚实说"未查询到"，绝不编。

- **Q：举一个反直觉发现？** 把 OCR 修干净后编造反而上升——干净文本让模型更自信发挥。数据质量↑ ≠ 产品质量↑。
- **Q：你做过最果断的产品决策？** 砍掉用户最想要的"上传方案查合规"——它直接撞"不下合规结论"红线 + OCR 质量风险，我把它降级为"列相关条文供自查"。**砍得清楚也是产品力**。
- **Q：你和 AI 怎么分工？** 我定义问题/定方案/定验收/卡红线/做迭代决策；AI 实现与草稿。我能判断对错、敢挑战它的结论。
